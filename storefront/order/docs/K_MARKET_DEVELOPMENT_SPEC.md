# 가락한상 오더 | 한국 전통시장 배달앱 개발 명세서 v1.1
기준일: 2026-11-02 | 브랜드: **가락한상 오더 (Garak Hansang Order)** | 상태: 시연 UI / 실거래 미연결

## 0. 목적과 포지셔닝
- 한국: **전통시장 상인 전용 입점 + 다점포 공동장바구니 + 시장 내 공동집하/공동배송**. 일반 프랜차이즈·일반 배달 음식점의 무차별 입점은 한국 사업의 우선 대상에서 제외한다.
- 동남아: 기존 범용 배달 플랫폼 명세서와 별도 서비스 지역 구성. 동일 핵심 주문 도메인을 확장하되 현지 배달·결제·규제 정책은 분리한다.
- 기존 가락한상 상호·로고·머리띠·수산물·채소 쟁반을 든 캐릭터의 동일성을 유지하고 레드 A 시안의 오토바이 캐릭터를 주문/배달 문맥에 활용한다.

## 2. 고객 앱 정보구조 및 화면 상세
- O-01: 온보딩 / 위치 권한 / 배송주소 및 시장 서비스가능권역 확인
- O-02: 홈 — 공식 가락한상 오더 브랜드, 마스코트, 시장별 탭, 카테고리 및 카테고리 사진, 쿠폰 캠페인, 당일 특가
- O-03: 시장 선택 — 가락/노량진/남대문/동대문/지역시장 + 각각 상인 수, 영업시간, 픽업/배송 표시(실데이터 연결 후)
- O-04: 검색 — 시장, 매장, 상품, 자동완성/최근 검색어(현 시연판은 문자열 검색)
- O-05: 매장 — 상인 인증상태, 사업자 정보, 영업시간, 휴무, 최소 주문, 신선도/취소 정책(상용화 시 필수)
- O-06: 상품 상세 — 이미지, 옵션, 판매단위, 원산지, 식품정보/알레르겐, 물류 조건, 품절·재고 버전
- O-07: 합배송 장바구니 — **시장 단위 grouping**, 점포별 소계/재고 잠금, 냉장/상온 분리, 배송 시간슬롯
- O-08: 쿠폰 — 마스코트 레드 브랜드, 발급 조건·대상 시장·사용기한·중복 제외, 할인 시뮬레이터
- O-09: 주문/결제 — 주문 분할/결제 멱등성/결제수단/카드 및 현금영수증/취소/환불
- O-10: 배달 추적 — 시장별 집하 → 품질검수 → 기사 픽업 → 배송 → POD 완료, 고객 ETA
- O-11: 마이 — 주문, 재주문, 즐겨찾기, 쿠폰, 알림수신 동의·철회
- O-12: 고객센터 — 챗/콜/사진 클레임, 판매점·라이더·플랫폼 귀책 분류, 환불
- O-13: 점주센터 — 상인 입점 심사, 정산, 영업일/출고 슬롯, 주문 상태, 상품 등록, 쿠폰 캠페인
- O-14: 기사/집하센터 — 시장구역 배차, 점포별 픽업 QR, 냉장 온도 기록, 합포장, 배송완료 증빙
- O-15: 운영자 — 주문 이벤트, 정산 대사, 사기/중복 청구, 쿠폰 예산, 사고/CS, 개인정보 열람 감사

## 3. 데이터 / 도메인 모델 (차기 백엔드)
기본 엔터티: Country, Market, MarketZone, Merchant, MerchantVerification, StoreSchedule, Product, ProductVariant, InventoryBatch, CountryOfOrigin, MerchantStock, Customer, Address, Cart, CartLine, FulfillmentGroup, ColdChainRequirement, FulfillmentSlot, Quote, Promotion, CouponIssuance, CouponRedemption, Order, OrderLine, OrderSplit, PaymentAttempt, PaymentLedger, Refund, StorePayout, Rider, DriverShift, DispatchJob, PickupProof, DeliveryProof, CustomerSupportTicket, AuditLog.

DB 기본키 UUID; `currency='KRW'`, integer won; 모든 변경 트랜잭션+불변 주문라인 스냅샷; 쿠폰은 발급/사용 서버 원장에 unique 제약; 배송 위치 데이터는 보존기간 제한. 시장/상인 테넌트별 RBAC. 주문 분할 및 정산은 `market_id`, `merchant_id`, `fulfillment_group_id` 구분.

## 4. 주문 및 합배송 처리 규칙
1. 고객 장바구니에 시장 A/B를 함께 담을 수 있으나 물류 그룹은 시장별로 분리. **시장 간 합배송 불가**.
2. 시장 A의 서로 다른 상인 물품을 모아 배송하려면 각 상인이 지정 시간 내 집하 완료를 보증해야 함.
3. 수산물과 상온 물품은 함께 주문 가능하더라도 적합한 온도 구획, 용기, 시간 제한이 갖춰지지 않으면 그룹을 분할. 질량/부피/식품 안전을 배송요율 산정에 반영.
4. 수산물은 가격 기준 (kg/마리/손질 후 중량) 표준화, 실중량 확정 전에 합의한 상한 초과 결제 금지.
5. 상인은 주문 수락 후 품절/대체품 요청을 처리하고 고객은 선택적 대체 승인. 부분 취소·부분 환불/배송비 재계산 지원.
6. 결제 전 재고 잠금 TTL, `Idempotency-Key`와 서버 시점 가격, 주문 스냅샷 저장. 이중 주문/결제 방지.
7. 시연판 예시 배송비 = 시장 기본료 + 추가 점포비 + 냉장 포장비. 비교 절약액은 배송 가정에 따른 계산값으로만 표기.

## 5. 전형적인 서버 API (후속 단계)
`GET /v1/markets`, `GET /v1/markets/{id}/zones`, `GET /v1/merchants?market_id=`, `GET /v1/catalog?market_id=`, `GET /v1/products/{id}`, `POST /v1/quotes`, `POST /v1/coupons/claim`, `POST /v1/coupons/validate`, `POST /v1/orders`, `GET /v1/orders/{id}`, `POST /v1/orders/{id}/cancel`, `POST /v1/payments/intents`, `POST /v1/webhooks/payment-provider`, `POST /v1/dispatch/assign`, `POST /v1/merchant/orders/{id}/accept`, `POST /v1/delivery/{id}/proof`, `GET /v1/merchant/settlements`. 
모든 쓰기 요청은 인증, 중복방지, 권한체크, 감사를 거치며 결제 웹훅의 서명과 재전송을 검증한다.

## 6. 실제 연동 전제
- 본 앱에는 **Neon/PG/배달기사/상인 실계정/결제 API를 연결하지 않음**. LocalStorage에서만 시연 장바구니·쿠폰·주문내역 저장.
- 상용 기술 권장: Android Kotlin/Compose or Flutter + 웹 PWA, Next.js Admin, Node API + Neon Postgres/PostGIS, Redis queue, Object Storage, FCM, 국내 PG 승인, 지도 및 배차 공급사 계약. 기술선정은 실수요와 라이선스 점검 후 확정.
- 국내 개인정보보호법, 전자상거래 소비자 보호, 식품 표시·판매자 책임, 위치정보/라이더 운송 계약, 전통시장 관련 지원사업 자격, 쿠폰 표시광고·경품법률 확인. 구체적인 의무는 사업 구조와 변경된 법령을 전문가가 검증해야 한다.
