실운영과 모의 환경이 서로 다른 이유

  • 기존 Neon products는 price_usd, orders는 total_usd·amount_krw, settlements는 USD 및 외부 소싱 정산 중심이다.
  • 로컬 v7 관리자는 정수 KRW 가격·상인별 정산·가상 주문 모델이다. 컬럼이 존재한다고 바로 양방향 동기화하면 환율·매출·원장 오류가 발생한다.
  • Vercel 프로덕션 데이터베이스가 어느 Neon 프로젝트를 가리키는지 확정한 후, 기존 테이블 덮어쓰기 금지, garak_ops 분리 스키마, 검증된 외부 ID로 참조 원칙을 적용한다.

3. 권장 순차 실행 로드맵 및 게이트

0단계. 원본/배포/DB 정본 확인 (최우선)

  • GitHub main 대 Vercel 배포 커밋 차이표 확보.
  • DATABASE_URL 값은 공개하지 않고 연결 프로젝트 ID만 검증.
  • 운영 데이터 백업을 확인하고 읽기 전용 기준선(상품·주문·카테고리/결제 상태 집계)을 고정.
  • 완료 기준: 실제 소스 체크아웃·Next.js npm ci && npm run build 통과, 스테이징 분리, 롤백 절차 검증.

1단계. 백엔드 보안·주문 원장 안정화

  • 주문 SKU 중복 합산, 원자적 재고 조건 차감, 상태 머신 우회 차단.
  • 비밀번호 변경 후 세션 폐기, 사업자 확인 상태 강제, 감사 로그.
  • 실결제는 Toss Sandbox 금액·중복 webhook 확인 전에 절대 활성화하지 않음.
  • 완료 기준: 실제 Neon 스테이징 100+ 동시 주문·취소·반품 테스트, 결제 불일치 0건, 중복 송금 0건.

2단계. 데이터·상품·콘텐츠 이식

  • 신선식품 카테고리 정리, 실판매 상품만 공개, 132 레시피 사진·문구 감수.
  • garak_ops 분리 스키마와 외부 ID를 적용, DB 마이그레이션 dry-run, 보안/복원 실험.
  • 완료 기준: 실상품 100% 상품 속성 확인, 운영 데이터와 대시보드 가격/재고·주문 합계 불일치 0건.

3단계. 판매자·미디어·광고·외부 채널

  • 상인/요리사 로그인과 신원 검증; Blogger·YouTube OAuth; 게시물 승인·광고 라벨.
  • 쿠팡 WING API 통합, 배민/쿠팡이츠는 공식 제휴 승인 범위에서만.
  • 완료 기준: 토큰 취소·게시물 비공개·API 실패·재시도 시나리오 검증, 허위 광고/노출 수치 0건.

4단계. 실제 운영 품질·앱·출시

  • 2번 시장스토리 디자인 전체 라우트 테스트, 모바일 375/390/430 및 데스크톱.
  • 접근성·검색 구조화 데이터, 안드로이드 앱, 성능·모니터링, 샌드박스 결제 후 운영 배포.
  • 완료 기준: 핵심 구매·취소·환불·배송·정산 실운영 조건 모두 Go 판정.

4. 이 보고서대로 이번 세션에 실제 수행한 작업

  1. 읽기 전용 외부 실사: GitHub/Vercel/Neon 두 프로젝트의 상태·스키마·테이블 존재 확인, 운영 DB 연결 프로젝트 미확정 기록.
  2. 기존 v6 자동 테스트 재실행: 베이스라인 통과.
  3. 로컬 베타 주문 안정화: 중복 SKU 합산·주문 수량 상한·조건부 재고 차감 적용. 기존 SQLite stock>=0 제약이 음수 재고를 이미 방지한다는 점도 실제 재현 검증.
  4. 관리자 보안: 비밀번호 회전시 기존 모든 세션 폐기, 신규 상품 공개시 상인 인증 조건, 활성 점포의 인증 철회 차단, 배송 상태 변경은 주문 상태 머신 경유.
  5. 백업/복원: tools/db_snapshot.py 개발. 스냅샷, 무결성 SHA256, 별도 경로 복원, 변조 거부, 덮어쓰기 거부 테스트.
  6. 통화 오류 방지: integrations/currency_contract.mjs 개발. 통화 단위 강제, 결제 금액 불일치 거부, 정수 원화 검증; 이 함수는 실 PG를 호출하지 않음.
  7. 자동 검증: Python 57건 + Node 통화 단위 테스트 3건, 동시 주문 50건, 공개 API 조회 100건, HTML 218개 링크·JS·UTF-8, 레시피 WebP 132개 점검.
